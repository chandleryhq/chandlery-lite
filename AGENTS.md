# chandlery-lite

This file is the project brief for any coding agent (Codex, Cursor, and others). Claude Code reads
the identical brief from `CLAUDE.md`; both are generated from one template, so they cannot
disagree — edit neither by hand.

Full-stack TanStack Start app deployed to **Cloudflare Workers** with **D1** as the database.

## Stack

| Area | Choice |
| --- | --- |
| Framework | TanStack Start + React 19 + Vite (file routes in `src/routes/`) |
| RPC | oRPC (`src/orpc/`), in-process client on the server, batched HTTP client in the browser |
| ORM | Drizzle ORM on Cloudflare D1 (dialect `sqlite`); migrations via wrangler |
| Auth | Better Auth 1.7, email + password, `tanstackStartCookies` adapter |
| UI | shadcn/ui + Tailwind v4 + lucide-react |
| Validation | zod 4 |
| Tests | vitest on workerd (`@cloudflare/vitest-plugin`), real D1 / KV / R2 emulation |
| Tooling | pnpm 11.1.2, Biome (format + lint), TypeScript, Wrangler 4 |

## Directory layout

```

  components/ui/       # shadcn components (managed by `shadcn add`, do not hand-edit)

test/                  # vitest (helpers.ts, setup.ts, worker.ts, stubs/)
```

Path alias: `#/*` -> `./src/*`.

## Common commands

```bash
pnpm dev                    # vite dev on port 3000 (local D1 via miniflare)
pnpm dev:setup              # apply migrations + seed to the local D1
pnpm check                  # biome check (format + lint)
pnpm typecheck              # tsc --noEmit (needs `pnpm cf-typegen` once)
pnpm test                   # vitest run (workerd)
pnpm cf-typegen             # regenerate worker-configuration.d.ts after editing wrangler.jsonc
pnpm db:generate            # drizzle-kit generate + flatten into migrations/
pnpm db:migrate:local       # apply migrations to the local D1
pnpm db:migrate:remote      # apply migrations to the deployed D1
pnpm db:seed:local          # run scripts/seed.sql against the local D1
pnpm build                  # vite build -> dist/server/wrangler.json
pnpm deploy:live            # migrate + build + wrangler deploy -c dist/server/wrangler.json
pnpm auth:generate          # regenerate src/db/auth-schema.ts from scripts/auth.config.ts
pnpm dlx shadcn@latest add <component>
```

The `pnpm` scripts above are the whole interface — there is nothing else to install and no wrapper
to learn. `deploy:live` is not called `deploy` because pnpm owns that word: `pnpm deploy` would run
pnpm's own workspace command instead of this script.

`pnpm deploy:live` and `pnpm db:migrate:remote` change the deployed app and its real database, and
are irreversible. Never run either on your own initiative — ask first, every time, even if the user
approved a deploy earlier in the session.

## Key conventions

- **Bindings come from `cloudflare:workers`**: `import { env } from "cloudflare:workers"`, never `process.env`. Use `db` from `#/db`; do not open connection pools.
- **One environment**: `wrangler.jsonc` has no `env.*` blocks, so `wrangler` commands never take `--env`. `database_id` stays `TODO-YOUR-D1-ID` until `wrangler d1 create` gives you a real one (or Cloudflare's deploy flow fills it in); until then everything that needs the database fails loudly rather than targeting nothing. Adding staging later means adding an `env.staging` block and building with `CLOUDFLARE_ENV=staging`.
- **Deploy builds first**: `vite build` writes `dist/server/wrangler.json`, and that is the config `wrangler deploy -c` takes. `pnpm deploy:live` does migrate, build and deploy in that order.
- **Schema flow**: edit `src/db/schema.ts` -> `pnpm db:generate` -> `pnpm db:migrate:local` -> tests -> `pnpm db:migrate:remote`. Never hand-write `drizzle/*` or `migrations/*.sql`; never edit an already-applied migration.
- **Auth schema**: Better Auth tables live in `src/db/auth-schema.ts`, generated by `pnpm auth:generate`; keep `scripts/auth.config.ts` plugins in sync with `src/lib/auth.ts`.
- **Secrets**: local in `.dev.vars` (gitignored, see `.dev.vars.example`); remote via `wrangler secret put <NAME>` after the first deploy. `BETTER_AUTH_SECRET` is required. `BETTER_AUTH_URL` is optional — leave it empty and Better Auth reads the origin from the request, which is what lets a one-click deploy work before there is a domain; set it once there is one, because a pinned origin beats one inferred from a header. `wrangler types` builds the `Env` type from the keys in `.dev.vars`, so a key that is missing there is a typecheck error, not a runtime surprise. Browser-visible values must be prefixed `VITE_` and live in `.env.local`.
- **oRPC**: build procedures from `publicProc` / `sessionProc` / `adminProc` in `src/orpc/middleware.ts`; group by domain in `src/orpc/router.ts`.
- **Commit gate**: `pnpm check && pnpm typecheck && pnpm test` must be green before committing. Route changes regenerate `src/routeTree.gen.ts`; never edit it by hand.

## Cloudflare hard limits

- **D1: max 100 bound parameters per statement.** A multi-row `db.insert().values([...])` expands to `columns x rows` params and fails silently above 100. Batch inserts by `floor(100 / columns)` rows.
- **Workflow steps must be idempotent.** A throwing `step.do()` re-runs the whole step, replaying side effects that already happened. Make writes safe to repeat or put them last; failed steps retry then give up silently while later steps continue.
- D1 and R2 `--location` is create-time only; neither D1 nor R2 can be renamed.
- Workers have no long-lived processes: no in-memory caches across requests, no pools; use KV / DO / Cache API.

## Definition of Done

A feature is done only when the whole slice is green; never report "backend done" as "done".

1. Data / service layer (schema + migration if needed).
2. oRPC procedure on the right builder (`publicProc` / `sessionProc` / `adminProc`) with zod input.
3. UI wired end to end with loading, empty and error states (no raw JSON dumps).
4. Tests in `test/` covering the happy path, an auth / permission failure and one error branch.
5. `pnpm check && pnpm typecheck && pnpm test` green.
6. Verified in the running app (`pnpm dev`), not only by typecheck.

Before replying "done", answer: which route is the entry point and did I open it? Is any procedure or UI left dangling? Are the three UI states drawn? If the frontend is deliberately deferred, list exactly what is missing.

## Collaboration notes

- **Deploys need explicit confirmation** from the user each time; the same goes for anything irreversible (dropping tables, deleting secrets or resources, force pushes).
